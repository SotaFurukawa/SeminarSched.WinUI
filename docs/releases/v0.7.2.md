# v0.7.2 (beta)

Status: Draft Release。v0.7.1公開後、実際に使ってみたユーザーからの追加報告「2時間経過しても最高品質のものが終わりませんでした。もう少し軽量な仕様にしてください...イメージだと45分くらいで終わらせて、残りの15分は合間合間でもう少し良いものがないか探索する時間です」（checkpoint 93）への対応。bug fixのためNext Version Ruleの既定に従いv0.7.2とした。

## ハイライト

- CP-SATの並列探索ワーカー数の上限（`CpSatScheduleSolver.ResolvedAutoSearchWorkers`）が、実は一度も実際の探索へ反映されていなかった不具合を修正した。すべての探索戦略が明示的にプロセッサ全コア分のワーカー数を指定していたため、v0.6.1〜v0.7.1で行ってきたワーカー数の引き下げは実質何も制限していなかった。
- 「高品質」「最高品質」の探索構成を、まず完成させることを優先する設計に見直した。最高品質は名目60分のうち約45分を「完成させる」ことに、残り約15分を「時間が余ったので改善を試す」ことに割り当てる（高品質も同じ比率）。以前は初期探索を5個の戦略に均等分割していたため1戦略あたりの持ち時間が短く（最高品質で1戦略あたり3.6分）、完成させること自体に失敗しやすかった。

## 主な変更点

### CP-SAT並列探索ワーカー数の制限が実際には効いていなかった不具合の修正
- `CpSatScheduleSolver.ResolvedAutoSearchWorkers`（論理コア数に応じた上限、`WorkerLimitEnabled`で有効/無効を切替）は、呼び出し元が`NumSearchWorkers: 0`（自動）のまま渡した場合にだけ適用される仕組みだった。ところが実際の探索戦略（`CpSatStrategies.cs`の`StandardCpSat`・`SeededCpSatA/B/C`・`AlternateDecision`・`MultiStage`・`HintImprovement`・`GrindingNeighborhoodRepair`・`GrindingFinalPolishing`のすべて）は、`NumSearchWorkers`に明示的にプロセッサの全論理コア数を渡していたため、この上限が一度も適用されていなかった。
- v0.6.1（論理コアの半分へ制限）・v0.7.0（さらに1/3へ）・v0.7.1（1/2へ戻す）と重ねてきたワーカー数の調整は、この不具合のため実際の探索に一切反映されていなかったことが判明した。実際にCPU負荷を抑えていたのはv0.7.0までのJob Object CPU rate control（v0.7.1で撤去済み）だけであり、それがアイドル時間まで浪費する副作用を持っていたことも合わせると、「CPUの制限をしたせいで最高品質が終わらない」というユーザーの推測は、まさにこの2つの不具合の組み合わせによるものだったと考えられる。
- 各探索戦略の`CpSatSolveOptions`構築処理から明示的なワーカー数指定を削除し、既定の0（自動）のまま`CpSatScheduleSolver`へ渡すようにした。これにより`ResolvedAutoSearchWorkers`の制限（および「CPU使用率を制限しない」チェックボックス）が、今回のversionで初めて実際の探索へ反映されるようになった。

### 「高品質」「最高品質」の探索構成の見直し（完成優先・改善は余り時間で）
- 従来は名目時間の65〜70%を初期探索・候補改善（5戦略への均等分割を含む）に、残り25〜40%を部分修復による改善に割り当てていた。初期探索の5戦略均等分割は、1戦略あたりの持ち時間を短くする（最高品質で1戦略あたり3.6分）ため、同じ問題を毎回ゼロから短時間で解き直す試行を繰り返すだけになり、完成（全コマ配置）に到達しにくい構成だった。
- 名目時間の75%（初期探索＋候補改善）を「まず完成させる」ことに、残り25%（部分修復＋最終調整）を「時間が余ったので改善を試す」ことに割り当てるよう再設計した。最高品質は名目60分なら45分/15分、高品質は名目30分なら22.5分/7.5分の比率になる。
- 初期探索の戦略数も、高品質は5→3、最高品質は5→4へ減らし、1戦略あたりの持ち時間を底上げした（最高品質の初期探索は1戦略あたり3.6分→7.5分)。

## 既知の未実装・保留

- 出力設定の表示項目ON/OFF・ロゴ画像・1ページの日数/講師列数・生徒別改ページ方式は引き続き未実装。
- 授業間隔の均等化・同一科目の連続抑制は、CP-SATの目的関数への近似的なソフト制約であり、常に理想的な結果を保証するものではない（v0.6.0から変更なし）。
- 検出したハードウェア性能（`SystemRequirements`）に応じて品質プロファイルの構成自体をさらに自動選択する、という踏み込んだ対応は今回も見送った。今回の2つの修正（ワーカー数制限が実際に効くようにしたこと、完成優先の時間配分）でどこまで改善するか実機で確認いただいたうえで、必要であれば追加対応を検討する。
