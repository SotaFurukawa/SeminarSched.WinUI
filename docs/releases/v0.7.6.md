# v0.7.6 (beta)

Status: Draft Release。ユーザー報告「やはり途中で停止してしまいます...何か致命的な課題がある気がします。確実にそれを見つけてください」（実際のプロジェクトファイルでの実行）への対応（checkpoint 97）。あわせて「2倍以上の時間を待ってもいい。既定の時間になっても終了しなかった場合に、そのまま継続する、という項目を追加してください」という新機能要望にも対応した。bug fixのためNext Version Ruleの既定に従いv0.7.6とした。

## ハイライト

- ユーザーの実際のプロジェクトファイルを直接使って調査した結果、grinding戦略（部分修復探索・延長フェーズ）の1回あたりの試行持ち時間が、実際の校舎データの規模に対して短すぎることを実測で特定した。最短の試行時間を10秒→30秒へ引き上げた。
- ⑤時間割自動作成の画面に「既定の時間になっても未配置が残っている場合、そのまま完成するまで継続する」設定を追加した（既定はい）。プロジェクトの既定値として保存でき、その回だけ一時的に変更することもできる。
- 上記の実装中、構造的に絶対完成しない問題（対応できる講師の空きが恒久的に不足している等）に対してこの新機能を有効にすると無限ループしてしまう重大な不具合を、テストスイート自体が実際にハングすることで発見・修正した。改善が得られない延長を検知したら自動的に打ち切る安全装置を追加した。

## 主な変更点

### 実際のプロジェクトファイルでの原因調査
- ユーザーから提供された実際のプロジェクトファイル（生徒75名・講師20名・受講希望83件・必要回数計458件・候補約39,475件）を直接使い、品質レベル1・3で自動作成を実行して原因を調査した（プロジェクトの複製に対してのみ実行し、元のファイルは一切変更していない）。
- CP-SATソルバー呼び出しに一時的な計測を追加したところ、この規模のデータでは、単発の90秒間の連続実行はfeasible解を見つけられる（約89秒とほぼ上限いっぱい）一方、grinding戦略の1回あたりの試行（既定で最短10秒）は多くの場合それだけでは不十分で、`Unknown`（feasible解にすら届かない）に終わることを直接確認した。実際に15秒の試行は失敗し、同じ状況で30秒の試行は複数回にわたり安定して成功（多くの場合458件全て配置済みの完全解）することを確認した。
- CP-SATモデルの構築自体（C#側）は約1〜2秒と高速で、ボトルネックではなかった。ボトルネックはCP-SATソルバー自身の内部処理（読み込み・presolve等、C#側の計測範囲外）にあり、この規模のモデルでは数秒〜十数秒かかる。短い試行時間の大半がこれに費やされ、実際の探索にほとんど時間が残らないまま打ち切られていたと考えられる。

### grinding戦略の試行持ち時間を引き上げ
- `GrindingStrategyBase`の`MinimumAttemptBudget`（最短の試行持ち時間）を10秒→30秒、`MaximumAttemptBudget`を60秒→90秒へ引き上げた（実測値に基づく）。checkpoint94で追加した「feasible解にすら届かなければ次回は倍にする」仕組みと組み合わせ、無駄な短時間失敗を減らす。

### 「既定の時間になっても終了しなかった場合、そのまま継続する」設定を追加
- `SchedulingPolicy`に`ContinueBeyondNominalTimeIfIncomplete`（既定true）を追加。⑤時間割自動作成の画面の「この回だけ探索の方針を変更する」セクション、および「①設定」の「スケジュール設定」タブの両方に設定項目を追加した。
- `ScheduleOptimizer`の延長フェーズを、従来の「1回のみ・名目時間の最大2倍で必ず打ち切る」から、この設定がオンの場合は「完成するかユーザーが『中断して現在の結果を採用』を押すまで、延長を繰り返す」方式へ拡張した。オフにすると従来通りの動作になる。

### 安全装置: 改善が得られない延長は自動的に打ち切る
- 上記の実装後の自己レビューで、対応できる講師が構造的に1人もいない・担当講師優先度5の絞り込みでその講師の空きが恒久的に不足している、といった「時間をいくら与えても絶対に解決しない」ケースに対してこの新機能を有効にすると、延長が無限に繰り返されてしまう重大な不具合を発見した（実際に、この状況を再現する既存のテストがテストスイート自体を本当にハングさせ、テストのホストプロセスを強制終了する必要があった）。
- 直近の延長パスが一切の改善をもたらさなかった場合（`GrindingNeighborhoodRepairStrategy`がヒントより良い結果を1つも見つけられなかった場合）は、そこで延長を打ち切るようにした。「時間が足りないだけ」なら次の延長で改善するはずなので、これは「構造的に不可能でも無限に粘る」ことを防ぎつつ、「時間さえあれば解決する」ケースでは粘り続けられる、両方を両立する設計になっている。
