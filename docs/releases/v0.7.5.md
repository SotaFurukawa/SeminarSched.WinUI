# v0.7.5 (beta)

Status: Draft Release。ユーザー報告2件（checkpoint 96）への対応。①「持ち時間内に完成しなかった場合、このパーセンテージが減少してしまう。これはおかしいので、初めから低く見えるようにしてください」。②「品質レベル3で実行したときに、部分修復探索（連続）(6/6)まで言っているにも関わらず、途中で強制終了されてしまいます。他の品質レベルでも見られます。2倍の時間が経っても、強制終了しないようにしてください」。bug fixのためNext Version Ruleの既定に従いv0.7.5とした。

## ハイライト

- **進捗パーセンテージが後退する不具合を修正**: 延長フェーズが始まった瞬間に表示が後退する（例: 100%付近から50%付近へ戻る）問題を、目盛りの設計自体を見直すことで解消した。延長が構造的に起こり得る実行では、通常ステージの進捗表示を最初から目盛りの半分（0〜50%）までしか使わないようにし、延長発生時はその続き（50〜100%）へそのまま進める。後退は一切発生しなくなった。
- **原因不明の強制終了を調査・修正**: 長時間の探索（特にgrinding戦略・延長フェーズ）の途中でアプリが理由もなく止まって見える不具合を調査し、CP-SATソルバー（`Google.OrTools.Sat.CpSolver`）のインスタンスを一度も破棄していなかった（ネイティブリソースリーク）ことを発見・修正した。あわせて、原因不明のまま実行が消えてしまう事態を避けるため、想定外の例外が起きた場合も必ずエラーメッセージを表示するようにした。

## 主な変更点

### 進捗パーセンテージの計算方式の再設計
- 従来（v0.7.0のcheckpoint91）は、延長が実際に発生した瞬間に「これまでの進捗と延長の持ち分を合計1.0になるよう事後的に比例配分し直す」方式だった。この再スケーリングにより、延長開始時点で表示が一度100%付近から後退することが分かっていたが、「少し時間を要しています」の警告と一緒に見せることで許容できると判断していた。しかし実際にはこの後退自体が「おかしい」というユーザー報告を受け、再設計した。
- `ScheduleOptimizer`に`ExtensionReservedShare`（0.5）を導入。延長が戦略registryに登録されている（＝構造的に起こり得る）実行では、通常ステージの進捗報告（`ProgressWeight`/`StrategyWeight`）を最初から0.5倍して報告するようにした。延長が実際に発生した場合は、この時点で目盛りの残り半分（0.5〜1.0）がそのまま未使用で残っているため、そこへ延長の進捗をそのまま割り当てるだけでよく、事後的な再計算・後退が一切不要になった。
- 延長が発生しない場合は、通常ステージ完了時点で（名目時間を使い切っていなくても）最大50%までしか進まないが、実行終了時（`OptimizationRunState`側の「実行中でなくなったら100%」という既存ロジック）に一度だけ100%へ前進する。

### パーセンテージの計算方法（ユーザー質問への回答）
- 経過時間と名目時間の比率ではなく、「計画済みの全戦略のうち、実際に完了・進行中の割合」（`OptimizationProgress.ProgressWeight`/`StrategyWeight`）を基準にしている。CP-SATは証明済み最適解に早期到達して名目の持ち時間よりずっと早く終わることが多く、経過時間ベースだと低いパーセンテージのまま止まって見えた後、終了の瞬間に100%へ飛ぶ問題があったため。
- 品質レベルごとの各ステージ（初期探索・候補改善・近傍再探索・仕上げ探索）には、名目時間に対する配分比率（`BudgetShare`）が設定されており、これをステージ内の戦略数で均等割りしたものが「1戦略あたりの重み」になる。戦略が完了するたびにこの重みを積み上げていく。
- 延長（GrindingNeighborhoodRepairStrategyが戦略registryに登録されている場合）が構造的に起こり得る実行では、上記の重みの合計を1.0ではなく0.5（半分）までしか使わない。残り半分は延長が実際に発生した場合のために予約されている。
- 画面表示用のパーセンテージ（`_displayedPercent`）は、上記の「真の目標値」へ200ミリ秒ごとに20%ずつ滑らかに追いつかせている（瞬間的な段差を視覚的になめらかにするため）。

### 原因不明の強制終了の調査・修正（CP-SATソルバーのネイティブリソースリーク）
- ユーザー報告「品質レベル3で6/6まで進んでいるのに途中で強制終了される。他の品質レベルでも見られる」を調査した。`CpSatScheduleSolver.Solve()`は探索1回ごとに新しい`Google.OrTools.Sat.CpSolver`インスタンスを生成していたが、このクラスは`IDisposable`（内部にネイティブ側のリソースを保持する）であるにもかかわらず、一度も`Dispose()`されていなかったことが判明した。
- grinding戦略（近傍再探索の連続試行、延長フェーズ）は同じ持ち時間の間に何十〜何百回も新規solveを繰り返す設計のため、この未破棄の`CpSolver`が試行のたびに積み重なり、実行時間が長くなるほどネイティブメモリが蓄積し続け、最終的にプロセスごと不可解にクラッシュしていた可能性が高い（.NET側の例外を経由しないネイティブメモリ不足によるクラッシュは、ユーザーから見ると「何の説明もなく強制終了された」ようにしか見えない）。この現象は品質レベルを問わず、grinding戦略・延長フェーズが十分長く走ればどの品質レベルでも起こり得るため、「他の品質レベルでも見られる」というユーザー報告とも一致する。
- `using var solver = new CpSolver { ... };`へ変更し、探索1回ごとに確実に破棄されるようにした。
- あわせて、`OptimizationRunState`の例外処理を広げた。従来は`InvalidOperationException`・`InvalidDataException`・`SqliteException`の3種類しか捕捉しておらず、それ以外の想定外の例外が発生した場合は実行中の表示がそのまま消えるだけで、成功・失敗どちらの通知も出ないまま止まって見える状態になっていた（バックグラウンドで実行しているタスクの例外が誰にも観測されないため）。すべての例外を捕捉してエラーメッセージを表示するようにし、今後同種の問題が万一残っていても、原因不明のまま消えることがないようにした。
- 「2倍の時間が経っても強制終了しないように」という要望について: 名目時間の最大2倍で打ち切るという設計自体（checkpoint90）は意図的なもので、無限に粘り続けないための安全装置として維持している。今回の修正はこの上限に達する前にクラッシュしてしまっていた問題への対応であり、上限自体は変更していない。

## 既知の未実装・保留

- 出力設定の表示項目ON/OFF・ロゴ画像・1ページの日数/講師列数・生徒別改ページ方式は引き続き未実装。
- 品質プロファイル（`OptimizationProfileCatalog`）自体のさらなる見直しは保留中（ユーザーからの明示的な要望あり、実装するまで毎回案内する）。
- CP-SATソルバーのリソースリークが実際に今回の強制終了の唯一の原因だったかどうかは、この環境では長時間の実行を再現できないため確証はない。実機で改善するかご確認いただきたい。万一まだ強制終了が起きる場合は、今回追加したエラーメッセージ表示・ログ（`%LocalAppData%\SeminarSched.WinUI\logs\`）から追加の手がかりが得られるはずなので、発生時の状況を教えてほしい。
- 延長フェーズの実機での見た目（後退が無くなったこと、通常ステージ完了時の前方向への段差の見え方）は、この環境からは確認できないため、実機でユーザーに確認をお願いしたい。
