# v0.7.7 (beta)

Status: Draft Release。v0.7.6公開直後の実プロジェクトファイルでの追加検証（checkpoint 98）で見つかった、
より根本的な不具合の修正。v0.7.6のcheckpoint97（grinding試行の最短時間の引き上げ、既定の時間を過ぎても
継続するトグル）は維持しつつ、その効果を大きく損なっていた真の原因を修正した。bug fixのためNext Version
Ruleの既定に従いv0.7.7とした。

## ハイライト

- v0.7.6公開後、ユーザーの実際のプロジェクトファイルで念のため再確認したところ、品質レベル3（標準）の
  実行で、個々の探索試行のほぼ全て（6/6の初期探索戦略＋延長フェーズの大半の試行）がCP-SAT側では
  Feasible/Optimalという成功結果を返しているにもかかわらず、最終的な結果は「時間割を作成できませんでした：
  すべての戦略で解が得られませんでした」という空の例外になる、という矛盾した挙動を直接確認した。
- 原因は、探索の持ち時間がちょうど尽きたタイミングで、.NET側のタイムアウト用キャンセル信号がCP-SAT自身の
  内部タイマーよりわずかに早く発火することがあり、そのせいで「既に良い解が得られているのに、直後の
  キャンセル確認で無条件にその解を捨てて例外にしてしまう」処理順序の不具合だった。この不具合はv0.7.6以前
  から存在していたと考えられるが、checkpoint97でgrinding試行の最短時間を10秒→30秒へ伸ばしたことで、
  試行が持ち時間いっぱいまで使うケースが大幅に増え、結果としてこの不具合の影響がむしろ悪化していた。
- 良い解（Feasible/Optimal）が得られている場合は、たとえキャンセル信号が同時に発火していてもその解を
  そのまま採用するよう修正した。これにより、v0.7.6で実装した「grinding試行の持ち時間を伸ばす」「既定の
  時間を過ぎても継続する」という対策が、本来期待した通りに効くようになった。

## 主な変更点

### 探索結果を捨てていた不具合の修正（根本原因）

- `CpSatScheduleSolver.Solve()`は、CP-SATソルバーの`Solve()`呼び出し直後に無条件で
  `cancellationToken.ThrowIfCancellationRequested()`を呼んでいた。呼び出し元（`ScheduleOptimizer`）は
  各戦略・各grinding試行に持ち時間ぴったりの`CancellationTokenSource`を設定しており、これは
  CP-SAT自身の`max_time_in_seconds`（同じ長さ）とは別々の時計で計測されている。.NET側の時計は
  モデル構築が始まる前から動き出す一方、CP-SAT側の時計は実際の探索が始まってから動き出すため、
  探索が持ち時間いっぱいまでかかった試行では、.NET側のキャンセル信号がCP-SAT自身の内部タイマーより
  先に発火することがしばしば起こる（`solver.StopSearch()`経由でCP-SATを早期終了させる、想定通りの
  仕組み）。このとき、CP-SATが既にFeasible/Optimalな解を見つけていても、直後の無条件な
  `ThrowIfCancellationRequested()`がその解をまるごと捨てて例外にしてしまっていた。
- 実際に、ユーザーの実プロジェクトファイル（生徒75名・受講希望83件・必要回数計458件）で品質レベル3
  （標準）を実行し、CP-SATの生の呼び出し結果を直接記録したところ、初期探索6戦略が全てFeasible、
  延長フェーズの試行も大半がFeasible/Optimalを返していたにもかかわらず、最終結果は空の例外になる
  現象を再現・確認した。
- 修正: Feasible/Optimalな結果が得られた場合はそれを優先して採用し、キャンセル確認は「良い結果が
  得られなかった場合」に限定するよう処理順序を入れ替えた（本当にキャンセルされた場合は従来通り
  `OperationCanceledException`として伝播し、探索が純粋に失敗した場合は従来通り
  `InvalidOperationException`を投げる）。

### 候補が1件も見つかっていない場合の延長猶予を追加

- 上記の根本原因調査の過程で、候補が1件も見つかっていない状態（`ScheduleOptimizer`内部の
  `bestBeforeExtension`がnull）のまま延長フェーズが1回丸ごと空振りした場合、既定の「継続する」設定
  （checkpoint97、v0.7.6）でも即座に諦めてしまう挙動を発見した。既に採用できる候補がある状態での
  「これ以上改善しない」ケース（諦めても失うものが無い）とは異なり、候補が1件も無い状態で諦めると
  ユーザーには何も残らない最悪の結果（例外のみ）になる。この状態に限り、追加の延長パス（既定5回分の
  猶予）を設けるようにした。候補が既にある通常のケースは、従来通り1回で見切りを付ける。
